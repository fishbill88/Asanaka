Asanaka build plan

A kanban board modelled on Asana’s Board view. The site will live on GitHub Pages, and the API and its own database will run in Docker on the VPS. Nothing has been built, committed or deployed yet. Use this page to check the plan, pick a design and answer six questions.

What gets built

Version 1 the board works end to end

  • Sidebar with projects, your name and Sign out.
  • Project header: name, member avatars, filters (all, my tasks, due this week), Add task.
  • Sections as columns: rename, task count, add a task at the top, menu (rename, move, delete), Add section, drag to reorder sections.
  • Cards: check circle, title, assignee, due date (red when late), priority and status chips, subtask and comment counts.
  • Drag cards within and across sections; the other cards make room; the board scrolls near the edges; keyboard and touch work too.
  • Inline “Add task” at the bottom of each section that stays open for the next one.
  • Task pane from the right with its own link: title, complete, assignee, due date, section, priority, status, description, subtasks, comments.
  • Completing a task: the check fills, a short celebration plays, the card settles in Done. Unticking puts it back where it was.

How the pieces connect

The API only answers requests from https://fishbill88.github.io. The API address is put into the website at build time from a GitHub setting, not from the code. It ends up visible in the browser anyway, because the browser has to call it, but it isn’t a password.

Accounts and passwords

admin: a password that rotates

  1. The password is 20 random characters, made on the VPS. It is never in the repo or on this PC’s disk.
  2. Rotating it updates the hash in the database and signs every admin session out at once. No restart needed.
  3. It rotates only when you ask. There is no schedule.
  4. rotate-admin-password.bat rotates it now and shows the new one; -Show shows the current one.

ameerperalta: your password, kept local

  1. The password sits in .secrets/users.local.json, which git ignores.
  2. seed-users.ps1 sends it to the server privately (on stdin), so it never shows in the repo, a command line or shell history.
  3. That also avoids a trap in this password: $$ turns into a process number in a shell, and into a single $ in a Docker settings file.

Worth knowing: the password you gave is short and common. The lock after 5 wrong tries protects it, but it should be changed after the first sign-in. The admin page in phase 7 can do that.

“Don’t mind the login for now” is read as: a simple sign-in page, but no sign-up, password reset or single sign-on.

VPS and deploys

What I found on the VPS

  • The server account can’t create folders in /opt, so Asanaka goes in its home folder.
  • Plenty of room: about 22 GB of free memory, 4 cores, 159 GB of disk.
  • Asanaka gets its own Docker project, its own database, a private port, and limits (API 0.5 CPU / 256 MB, database 512 MB). The other services are left alone.
  • Nightly database backup, 14 kept.

The one step you run yourself

  • Giving the API its web address needs the server account’s sudo password, so you run vps\host-setup.bat once and type it.
  • It restarts the web server, which drops every site on the box for about a second. Question 4 picks the time.

Website deploys

Push to main, and GitHub builds the site and publishes it to the GitHub link.

API deploys

deploy-vps.bat copies the API to the VPS, rebuilds it, waits for its health check and keeps the last five releases. The database is never rebuilt. A smoke test then signs in, adds, moves, completes and deletes a task.

Risks

A shared VPS

A runaway container could starve the other services. The memory and CPU limits stop that.

The API’s web address

It comes from sslip.io, a free service that turns an IP address into a name. If it disappears, the API needs a real domain: one web server line and one GitHub setting.

Sign-in tokens in the browser

Any script running on the page could read them. A strict content policy and no third-party scripts on the app keep that risk small.

A weak user password on a public page

Locked after 5 wrong tries for 15 minutes. Change it after the first sign-in.
